Optional integration targets use this shape:

```hcl
{
  name       = string
  endpoint   = string
  model_uuid = string
  url        = optional(string)
}
```

When an optional integration is configured, `name`, `endpoint`, and `model_uuid` must be non-empty. If the target is cross-model from any MongoDB application that needs it, `url` must contain an offer URL created outside this module.

COS agent integrations are same-model and keyed by the config server or shard app name. Use one subordinate target per principal MongoDB application:

```hcl
cos_agent_integrations = {
  "config-server" = {
    name     = "opentelemetry-collector-config"
    endpoint = "cos-agent"
  }
  "shard-one" = {
    name     = "opentelemetry-collector-shard-one"
    endpoint = "cos-agent"
  }
  "shard-two" = {
    name     = "opentelemetry-collector-shard-two"
    endpoint = "cos-agent"
  }
}
```

### Sensitive configurations and secrets

The module takes TLS private keys and object-store credentials as ephemeral variables and stores them in Juju secrets through the provider's write-only `value_wo` attribute. Terraform sends them to the Juju controller during apply and writes `null` for the write-only value to `terraform.tfstate`. Ephemeral credentials are also omitted from saved plans.

Each secret has a version number that controls creation, rotation, and removal. `count` cannot read an ephemeral credential, so the version is the switch. The S3 access key and secret key are fields of one Juju secret and share `s3_secret_version`.

| Version         | Credential | Result                                           |
| --------------- | ---------- | ------------------------------------------------ |
| `0` (default)   | unset      | no secret                                        |
| `1`             | set        | secret created, revision 1                       |
| `2`             | new value  | in-place update, revision 2                      |
| `2` (unchanged) | unset      | no changes                                       |
| `0` again       | unset      | secret and grant destroyed, nothing else touched |
| `1` again       | set        | new secret, revision 1                           |


| Credential inputs                      | Version input                                  | Required secret keys                |
| -------------------------------------- | ---------------------------------------------- | ----------------------------------- |
| `config_server_tls_client_private_key` | `config_server_tls_client_private_key_version` | `private-key` (PEM)                 |
| `config_server_tls_peer_private_key`   | `config_server_tls_peer_private_key_version`   | `private-key` (PEM)                 |
| `s3_access_key`, `s3_secret_key`       | `s3_secret_version`                            | `access-key`, `secret-key`          |
| `gcs_secret_key`                       | `gcs_secret_version`                           | `secret-key` (service-account JSON) |

Declare ephemeral variables in the root module and forward them to the product module. For example, with the required application inputs already configured:

```hcl
# 1. Root module declares an ephemeral variable to receive the environment variable.
variable "config_server_tls_client_private_key" {
  type      = string
  sensitive = true
  ephemeral = true
  default   = null
}

# 2. Forward the variable into the product module.
module "sharded_cluster" {
  source = "./terraform/product/sharded_cluster"

  config_server_tls_client_private_key         = var.config_server_tls_client_private_key
  config_server_tls_client_private_key_version = 1
  # ... required config_server, mongos and data_integrator application inputs ...
}
```

Supply credentials through environment variables or command-line flags, at plan and at apply. Export only the credentials you need, and declare and forward each root variable as shown above:

```bash
export TF_VAR_config_server_tls_client_private_key="$(cat client-tls.key)"
export TF_VAR_config_server_tls_peer_private_key="$(cat peer-tls.key)"
export TF_VAR_s3_access_key="..."
export TF_VAR_s3_secret_key="..."
export TF_VAR_gcs_secret_key="$(cat service-account.json)"

terraform plan -out=tfplan
terraform apply tfplan
```

Keep credentials out of `.tfvars` files. Keep version numbers in your non-sensitive configuration for subsequent runs. Backup credentials require the matching `backups_integrator.storage_type` (`s3` or `gcs`); a nonzero version without the matching integrator is rejected.

To rotate a secret, update the credential in your environment and increment the matching version variable, for example `config_server_tls_client_private_key_version = 2`. For S3, supply both keys and increment `s3_secret_version`. Changing a credential without changing the version has no effect and produces no warning. Terraform only needs the credential on runs that create or rotate the secret. Any other plan or apply works with it unset.
